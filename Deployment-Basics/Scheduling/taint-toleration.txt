Good attempt. Some parts are right, a few need fixing, and for #5 I’ll show you both forms.

1) one-tol: right

one-tol tolerates dedicated=gpu:NoSchedule but not team=ml:NoSchedule. A pod needs a toleration for every NoSchedule taint on the node, so one missing toleration blocks it. The PreferNoSchedule taint (tier) is soft and doesn’t block.

2) two-tol: right idea, but one correction

You wrote “team has preferNoSchedule”, but that’s mixed up. In the setup:

dedicated=gpu:NoSchedule and team=ml:NoSchedule are hard taints.
tier=batch:PreferNoSchedule is the soft one.

So two-tol tolerates both hard taints and runs. The reason for /tmp/t3-prefer.txt is: PreferNoSchedule is only a preference, so the scheduler tries to avoid the node but will still use it when nothing else fits. Here node01 is the only schedulable node.

3) key-only: not quite

Your file tolerates dedicated and team, but it still has effect: "NoSchedule" on both. The task said “by key only”, meaning no effect and no value. Remove the effect lines:

yaml
spec:
  tolerations:
  - key: dedicated
    operator: Exists
  - key: team
    operator: Exists
  containers:
  - image: nginx
    name: key-only

With no effect, the toleration matches that key with any effect (NoSchedule, PreferNoSchedule and NoExecute). Fix the indentation too: the blank lines are fine, but keep containers: at the same column as tolerations:.

4) wrong-effect: right

The toleration says NoExecute, but the taint’s effect is NoSchedule. The effect has to match, so the toleration doesn’t apply. Also, wrong-effect only tolerates dedicated, so it would still be blocked by team even with the right effect. Write the reason as: toleration effect NoExecute does not match the taint's effect NoSchedule, so it doesn't apply.

5) Removal: the two forms

bash
# form 1: remove one specific taint (exact key=value:effect)
k taint node node01 team=ml:NoSchedule-

# form 2: remove ALL taints with that key, any value or effect
k taint node node01 dedicated-

You already knew form 2. Form 1 is the one that removes only a single taint. A third variant, key:Effect- (for example dedicated:NoSchedule-), removes only that effect for the key. Put both commands in /tmp/t3-remove.txt.

6) NoExecute taint: your answer needs checking

wrong-effect tolerates dedicated=gpu:NoExecute, so it survives. That’s the whole point of its odd toleration.
one-tol was Pending, so there’s nothing to evict.
two-tol and key-only ran. two-tol has NoSchedule tolerations only, so the NoExecute taint evicts it. key-only, once you remove the effect line, has no effect set, so it tolerates NoExecute too and survives.

So the survivors are wrong-effect and (after your fix) key-only. Verify:

Question 5 is nearly all correct. Item 3 needs the actual taint name, and item 6 has one point backwards.

1) Causes: all three correct

app-a: the toleration value is production, but the taint value is prod. With Equal, the value must match exactly.
app-b: the toleration effect is NoExecute, but the taint’s effect is NoSchedule. The effect must match, or be omitted.
app-c: keys are case-sensitive, so Env doesn’t match env.

2) Running: correct

All 6 pods are Running. Check they’re on node01 with k get pods -n taint5 -o wide.

3) Cordon: right field, but the task asked for the taint

Unschedulable: true is the node field. The taint that cordon adds shows up on the Taints: line:

node.kubernetes.io/unschedulable:NoSchedule

Write that to /tmp/t5-cordon.txt. It’s the NoSchedule effect, which is why cordon doesn’t touch running pods.

4) New pods Pending: correct

The two new app-a pods are Pending because the node is cordoned and controlplane is tainted. After k uncordon node01, they schedule by themselves, since the app-a toleration now matches env=prod.

5) Drain: correct reasoning

Drain cordons the node and then evicts the pods. The Deployments recreate them, but both nodes now reject them: node01 is cordoned, and controlplane has the control-plane taint, which none of the pods tolerate. So all 6 stay Pending. Your flags work, with two notes:

--ignore-daemonsets is required because of the cilium pods.
--force was not needed here. It’s only for bare pods with no controller, which would be deleted permanently. --delete-emptydir-data is only needed if a pod uses an emptyDir volume.

6) Cordon vs NoExecute: one point is backwards

You wrote that cordon is “strict”. It’s actually the weaker of the two. Put this in /tmp/t5-diff.txt:

cordon = NoSchedule only: new pods are blocked, running pods stay.
NoExecute taint = also evicts running pods that don't tolerate it.
drain = cordon + evicts the pods (respecting PodDisruptionBudgets) so controllers recreate them elsewhere; cordon alone never moves anything.

What this set drilled

A pod must tolerate every NoSchedule and NoExecute taint on a node, and the key, value and effect must all match.
A toleration only permits. To dedicate a node you need taint plus toleration, and label plus nodeSelector or affinity.
operator: Exists with no key is the wildcard used by system DaemonSets.
NoSchedule blocks new pods, NoExecute also evicts, and tolerationSeconds delays that eviction.
Cordon is a built-in NoSchedule taint, and drain is cordon plus eviction.

That finishes scheduling: nodeSelector, node affinity, taints and tolerations. A natural next set is pod affinity and anti-affinity with topologyKey, or resource requests, limits and LimitRange, which also cause Pending pods. Which one do you want?
